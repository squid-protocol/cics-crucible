# gt-post-wait-event: POST, WAIT EVENT and terminal CONVERSE

## The trap

`GTPOST` (transaction `GT61`) takes a mode letter from the typed input
(`RECEIVE INTO(WS-HEAD) MAXLENGTH(6) NOTRUNCATE`, which leaves the rest of the input) and writes
one line to TS queue `GTLOG`:

* `W`: `POST AFTER SECONDS(5) REQID('GTPOSTW') SET(ptr)`, then reads the 4-byte area through
  `SET ADDRESS OF LS-TEC TO ptr`, `WAIT EVENT ECADDR(ptr)`, reads the area again, then
  `CANCEL REQID('GTPOSTW')`.
* `N`: `WAIT EVENT ECADDR` of a null pointer.
* `P`: `POST TIME(090000) REQID('GTPOSTP') SET(ptr)` at 10:00:00.
* `F` / `C`: `CONVERSE FROM(8 bytes) FROMLENGTH(8) INTO(10-byte area) TOLENGTH(n)` with n = 10
  (`F`) or 4 (`C`); the reply is the rest of the operator's input.

## Why a naive translation breaks

* POST/WAIT EVENT are old-style commands that translators refuse whole, or model as a no-op
  wait: the area then never changes and a program testing the posted bytes loops or misreads.
* The area is storage CICS owns and hands back by pointer; a port that returns a copy hides the
  posting from the program's own record.
* The POSTed request is gone once it expired, so CANCEL of its REQID is NOTFND. A port that
  keeps the request around answers NORMAL.
* CONVERSE is a SEND plus a RECEIVE. A port that drops the send, or that lets TOLENGTH grow the
  area, misses the LENGERR cut and the original length in TOLENGTH.

## Expected behaviour

Model (SPEC sections 2 and 4): T001 is a 24x80 3270 display; the scenario starts at 10:00:00
with `GT61 <mode>...` typed on it. POST and WAIT EVENT record no event (SPEC 6.2 has none for
them): the program's own breadcrumb in `GTLOG` and the CANCEL event are what a runner compares.
RESP values are EIBRESP numbers: NORMAL 0, NOTFND 13, INVREQ 16, LENGERR 22, EXPIRED 31
[RESP-CODES].

* **`post-wait-cancel`** (input `GT61 W`, 6 bytes, so the first RECEIVE takes it all).
  * POST: "This 4-byte control area is initialized to binary zeros", and SET returns "the
    address of the 4-byte timer-event control area generated by CICS" [POST]. RESP 00; the area
    reads `LOW-VALUES` (`ZERO`).
  * WAIT EVENT: ECADDR "specifies the address of the timer-event control area that must be
    posted before task activity can be resumed" [WAIT-EVENT]. The area is posted when the
    time expires: "its first byte is set to X'40' and its third byte to X'80'" [POST]. The task
    resumes, RESP 00, and the program sees bytes 1 and 3 as X'40' and X'80' (`POSTED`).
  * CANCEL REQID('GTPOSTW'): the POST's request expired when the wait ended, so the request
    is not found: NOTFND [CANCEL] (CANCEL event, `resp` NOTFND). Line:
    `W POST=00 ZERO WAIT=00 POSTED CANCEL=13`.
* **`wait-null`** (`GT61 N`): "INVREQ RESP2 2" for a null ECADDR pointer [WAIT-EVENT].
  Line: `N WAIT=16 R2=02`.
* **`post-expired`** (`GT61 P`): TIME(090000) at 10:00:00 is already past; EXPIRED "if the
  specified time has already passed" [POST]. The program does not read the SET pointer.
  Line: `P POST=31`.
* **`converse-fits`** (`GT61 FREPLY`): the first RECEIVE takes `GT61 F` and keeps `REPLY`.
  CONVERSE writes `GT61 ASK` (SEND-TEXT event, 8 bytes, no options) and reads the reply INTO
  the 10-byte area with TOLENGTH 10 as the most accepted: 5 bytes fit, NORMAL, TOLENGTH set to
  5, the other 5 bytes of INTO unchanged (`.`) [CONVERSE]. Line:
  `F CONV=00 TOLEN=0005 REPLY.....`.
* **`converse-cut`** (`GT61 CABCDEFGH`): TOLENGTH 4, the reply is 8 bytes: LENGERR, INTO gets
  `ABCD`, "the TOLENGTH area is set to the original data length", 8 [CONVERSE]. Line:
  `C CONV=22 TOLEN=0008 ABCD......`.

## What a correct port must do

* Make POST's area a block the program's pointer addresses: zeros until a WAIT EVENT posts it
  (X'40', byte 3 X'80'); a null ECADDR is INVREQ RESP2 2; a past TIME is EXPIRED.
* Treat an expired POST as no longer cancellable (CANCEL NOTFND).
* Send CONVERSE's FROM as a plain SEND, then read the reply with RECEIVE rules (cut = LENGERR,
  TOLENGTH the original length, INTO only the bytes that fit).

## Avoided ambiguities

* **A second POST ends the first area.** IBM: "A task can have only one active POST at a time";
  a later POST releases the earlier area and a WAIT EVENT on it is "unpredictable" [POST].
  The #5079 class sweep lists this member, but no scenario reaches it: no behaviour is stated
  to hang a log on. A runner refuses it by name.
* **CANCEL of an unexpired POST** (does it post the area?) is not stated for the same task; the
  case cancels only after the wait.
* **WAIT EVENT on an already posted area**, **a POST with no REQID** (generated name) and **the
  SET pointer after EXPIRED** are not stated by IBM; the program gives a REQID, waits once and
  never reads the pointer after EXPIRED.
* **POST TIME equal to the current time**: the case uses an hour earlier.
* **Clock-driven posting** (another task's CANCEL, polling with SUSPEND): one task runs.
* **The CONVERSE reply.** IBM's reply is a terminal input after the send; the harness has one
  operator input per step, so the reply is the rest of it after a NOTRUNCATE RECEIVE (README
  lower-confidence table). CONVERSE on an LUTYPE2 terminal (EOC) and the APPC forms are not used.
